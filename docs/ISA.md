## Архитектурные принципы

- 32-битная арифметика и 32-битные инструкции
- раздельная память команд и память данных (Гарвардская архитектура)
- байтовая адресация данных; только `lw`, `sw`, `lb`, `lbu`, `sb` обращаются к RAM
- арифметика не меняет флаги `NZVC`: условия проверяются сравнением и ветвлением
- результат любой арифметической операции -- младшие 32 бита математического результата
- ошибки во время исполнения -- `trap` с явным кодом, а не флаги

## Память данных

### Организация RAM

Память не делится на заранее зарезервированные области фиксированного размера:
- статические данные, константы и строковые литералы размещаются от адреса `0` (их конец `static_end` известен после компиляции)
- указатель кучи `HP` изначально равен `static_end`; `new` и `input()` выделяют память вверх, без `free`
- указатель стека `SP` получает размер RAM до первой инструкции и растёт вниз
- при выделении памяти куча не должна пересекать стек; нарушение приводит к `trap 3`
- запрос массива выше максимума, вычисленного из `RAM_SIZE`, также приводит к `trap 3`

```
┌─────────────────────────────────────┐
│ СТЕК (растёт вниз)                  │
│ SP стартует в RAM_SIZE = 1 МБ       │
│                                     │
├─────────────────────────────────────┤◄── SP (первый свободный байт)
│ СВОБОДНАЯ ОБЛАСТЬ                   │
├─────────────────────────────────────┤◄── HP = static_end
│ КУЧА (растёт вверх)                 │
│ new int[n], input()                 │
│                                     │
├─────────────────────────────────────┤
│ СТАТИКА (0 .. static_end-1)         │
│ строки, true/false, INT_MIN,        │
│ константы, заголовки массивов       │
└─────────────────────────────────────┘
```

### Выравнивание

`lw`/`sw` требуют адрес, кратный 4, иначе `trap 2`. `lb`/`lbu`/`sb` работают с любым адресом. Транслятор размещает слова и массивы по выровненным адресам, поэтому невыровненный доступ возможен только как ошибка программы.

### Массивы

Первое слово -- количество элементов, далее -- сами элементы. Ссылка указывает на слово длины. `len()` и проверку границ генерирует компилятор по этому слову. `new int[n]` обнуляет каждый выделенный элемент; это обеспечивает нулевое начальное значение без очистки неиспользуемой RAM при запуске. Для `new int[n]` кодогенератор также проверяет, что `n` не превышает `(RAM_SIZE - 4) // 4` из `src/machine/config.py`: 4 байта занимают заголовок, остальные отведены под элементы. Превышение приводит к `trap 3`; реальный допустимый размер может быть меньше из-за статики, уже выделенной кучи и стека.

### Строки

Строки -- null-terminated последовательности байтов.

### Статическая память

- адреса 0--3 -- нулевое слово: на байт 0 ссылаются `str` без инициализатора, а на слово по адресу 0 -- неинициализированные массивы с длиной 0; любой их индекс приводит к `trap 4`
- целочисленные значения в диапазоне знакового `imm16` кодируются как `addi Rd, R0, imm`; остальные хранятся в статике и загружаются командой `lw Rd, imm16(R0)`
- кодогенератор ограничивает размер статики значением `MAX_STATIC_SIZE` из `src/machine/config.py`, равным 32 * 1024 - 4 = 32764 байтам; это наибольший размер, кратный четырём, который помещается в знаковый `imm16` при инициализации `HP`

### Начальное состояние модели

- при сбросе предполагается `PC = 0`; `R0` всегда равен нулю; значения неинициализированной RAM не определены
- размер RAM задаётся `RAM_SIZE` в `src/machine/config.py` и сейчас равен 1024 * 1024 байтам; целевая модель устанавливает `SP` (`R2`) в это значение перед запуском первой инструкции
- стартовый код транслятора задаёт `HP` (`R8`) командой `addi HP, R0, static_size`; размер статики ограничен `MAX_STATIC_SIZE` и помещается в знаковый `imm16`
- режим с `main` вызывает `main`; режим без `main` вызывает синтетическую функцию скрипта с обычным ABI-кадром; после возврата выполняется `halt`

### Прочее

- неинициализированные локальные переменные семантически нельзя читать до присваивания; кодогенератор технически записывает ноль в их слоты; элементы `new int[n]` обнуляются генератором при выделении; неиспользуемая RAM при запуске не очищается
- `input()` использует `INPUT_BUFFER_SIZE` из `src/machine/config.py`: сейчас это 1024 байта на вызов, включая завершающий `\0`, поэтому допускается до 1023 байт текста
- размещение байтов в слове -- little-endian: младший байт по меньшему адресу
- программа без `main` исполняется как скрипт сверху вниз; скриптовые переменные живут в кадре скрипта на стеке, как локальные одной неявной функции

Начальное состояние машины и формат `.bin`, описанные выше, -- контракт модели процессора и загрузчика: 4 байта `static_size` (little-endian), затем `static_size` байт образа статики (первое слово образа -- нулевое, адреса 0--3), затем инструкции. `static_size` кратен 4 и включает padding; каждое слово инструкции также little-endian.

## Регистры

32 регистра по 32 бита (`R0`--`R31`):

- `R0` -- всегда ноль; запись игнорируется
- `R1` (`RA`) -- адрес возврата
- `R2` (`SP`) -- указатель стека
- `R3` (`FP`) -- указатель кадра функции
- `R4`--`R7` -- аргументы функции; `R4` также содержит результат
- `R8` (`HP`) -- зарезервированный указатель кучи; обычный codegen не использует его как временный, процедуры выделения памяти обновляют его глобально
- `R9`--`R31` -- временные регистры

`FP` даёт постоянную базу локальным переменным, пока `SP` сдвигается при вычислении выражений. Соглашение вызовов:
- `SP` указывает на первый свободный байт; стек растёт вниз
- аргументы 1--4 передаются в `R4`--`R7`; 5-й и далее вызывающий кладёт в стек перед `jal` в порядке следования -- 5-й по младшему адресу, каждый следующий над предыдущим, после возврата снимает; в вызываемой 5-й аргумент лежит по `4(FP)`, 6-й -- по `8(FP)`
- результат функции -- в `R4`
- пролог: `addi SP, SP, -8`; `sw FP, 4(SP)`; `sw RA, 0(SP)`; `addi FP, SP, 4`; `addi SP, SP, -N` (N -- размер локальных)
- доступ: `RA` по `-4(FP)`, старый `FP` по `0(FP)`, локальные -- по отрицательным смещениям от `FP` начиная с `-8(FP)`
- эпилог: `addi SP, FP, -4`; `lw RA, 0(SP)`; `lw FP, 4(SP)`; `addi SP, SP, 8`; `jr RA`
- вызываемая обязана восстановить `R1`, `SP`, `FP`; `R4`--`R7` и `R9`--`R31` она вправе портить; `R8` не сохраняется кадром, а зарезервирован под глобальный `HP` и меняется только процедурами выделения памяти
- выделение кадра, аргументов и временное сохранение регистров уменьшают `SP`; генератор проверяет пересечение с кучей в процедурах выделения динамической памяти, но не перед каждым сдвигом стека

### Пролог и эпилог функции

Пролог:
```asm
   addi SP, SP, -8  # отводим 8 байт под RA и старый FP
   sw   FP, 4(SP)   # сохранить старый FP
   sw   RA, 0(SP)   # сохранить RA
   addi FP, SP, 4   # FP = SP + 4 -- новая база кадра
   addi SP, SP, -N  # место под локальные (N -- суммарный размер локальных)
```

Расположение кадра в памяти (адреса относительно FP):
```
┌─────────────────────────────────────┐
│ предыдущий кадр (вызывающая функция)│◄── FP + 4
├─────────────────────────────────────┤
│ старый FP (сохранён прологом)       │◄── FP + 0
├─────────────────────────────────────┤
│ RA (адрес возврата)                 │◄── FP - 4
├─────────────────────────────────────┤
│ локальная переменная 1              │◄── FP - 8
│ локальная переменная 2              │◄── FP - 12
│ ...                                 │
├─────────────────────────────────────┤
│ первый свободный байт               │◄── SP (конец кадра)
└─────────────────────────────────────┘
```

Эпилог:
```asm
   addi SP, FP, -4  # подъём к RA (SP = FP - 4)
   lw   RA, 0(SP)   # восстановить RA
   lw   FP, 4(SP)   # восстановить старый FP
   addi SP, SP, 8   # освободить кадр
   jr   RA          # возврат в вызывающую
```

Эпилог выше -- каноническая последовательность; кодогенератор в [codegen.py](../src/translator/codegen.py) реализует эквивалент: читает RA и старый FP прямо по FP (`lw RA, -4(FP)`, старый FP -- во временный регистр, обычно `R9`), затем `addi SP, FP, 4`, `mv FP, R9`, `jr RA`; обе версии -- пять инструкций, смысл тот же: восстановить RA, FP и SP, затем вернуться.

## Форматы инструкций

Все форматы занимают 32 бита, `Op` -- биты 31--26. Неиспользуемые поля -- нули. Модель содержимое неиспользуемых бит не проверяет: требование нулей -- обязанность транслятора.

| Формат | Поля |
| --- | --- |
| `R` | Op:6, Rd:5, Rs1:5, Rs2:5, zero:11 |
| `I` | Op:6, Rd:5, Rs1:5, Imm:16 |
| `S` | Op:6, Rs2:5, Base:5, Off:16 |
| `B` | Op:6, Rs1:5, Rs2:5, Disp:16 |
| `J` | Op:6, Disp:26 |

Обращение к памяти: эффективный адрес = `Base + Off`. Для `jr` используется специальная I-образная раскладка `Op:6, zero:5, Rs:5, zero:16`, где `Rs` занимает биты 20--16. Для `out` используется специальная S-образная раскладка `Op:6, Rs:5, zero:5, Port:16`; `Rs` занимает биты 25--21, номер порта -- биты 15--0.

Знаковость: `Imm`, `Off`, `Disp` -- знаковые; immediate у `lui`/`ori` -- беззнаковый (половины константы).

Смещения переходов измеряются в инструкциях и отсчитываются от следующей команды. 26-битный знаковый `Disp` принимает значения от `-2^25` до `2^25 - 1` инструкций, то есть переход охватывает примерно 128 МиБ в каждую сторону. Ветвления формата `B` принимают значения от `-2^15` до `2^15 - 1` инструкций, то есть примерно 128 КиБ в каждую сторону.

Функция `listing_line` формирует строку листинга вида `<адрес> - <HEX> - <мнемоника>` для инструкции и саму запись файла не выполняет. Кодирование выполняется по реальным командам и номерам регистров.

## Кодирование опкодов

Старшие 2 бита опкода задают класс формата: `00` -- `R`, `01` -- `I`, `10` -- `S`, `11` -- `B`/`J`/системные; внутри класса команда различается младшими 4 битами.

`R`-класс, опкод `00xxxx`:

| Биты | Код | Команда |
| --- | --- | --- |
| `000000` | 0 | `add` |
| `000001` | 1 | `sub` |
| `000010` | 2 | `mul` |
| `000011` | 3 | `div` |
| `000100` | 4 | `mod` |
| `000101` | 5 | `and` |
| `000110` | 6 | `or` |
| `000111` | 7 | `slt` |
| `001000` | 8 | `seq` |
| `001001`--`001111` | 9--15 | резерв |

`I`-класс, опкод `01xxxx`:

| Биты | Код | Команда |
| --- | --- | --- |
| `010000` | 16 | `addi` |
| `010001` | 17 | `lui` |
| `010010` | 18 | `ori` |
| `010011` | 19 | `lw` |
| `010100` | 20 | `lb` |
| `010101` | 21 | `lbu` |
| `010110` | 22 | `jr` |
| `010111` | 23 | `in` |
| `011000`--`011111` | 24--31 | резерв |

`S`-класс, опкод `10xxxx`:

| Биты | Код | Команда |
| --- | --- | --- |
| `100000` | 32 | `sw` |
| `100001` | 33 | `sb` |
| `100010` | 34 | `out` |
| `100011`--`101111` | 35--47 | резерв |

`B`/`J`/системный класс, опкод `11xxxx`:

| Биты | Код | Команда |
| --- | --- | --- |
| `110000` | 48 | `beq` |
| `110001` | 49 | `bne` |
| `110010`--`110011` | 50--51 | резерв |
| `110100` | 52 | `jmp` |
| `110101` | 53 | `jal` |
| `110110`--`111101` | 54--61 | резерв |
| `111110` | 62 | `trap` |
| `111111` | 63 | `halt` |

Неиспользуемые коды опкодов -- `trap` «неизвестная команда».

## Набор команд

| Группа | Команды | Семантика |
| --- | --- | --- |
| арифметика (`R`) | `add`, `sub`, `mul`, `div`, `mod` | целочисленная; `div` -- округление к нулю, `mod` -- знак делимого |
| логика и сравнение (`R`) | `and`, `or`, `slt`, `seq` | побитовые над словами; `slt` -- знаковое сравнение, `seq` -- равенство; результат -- `1`/`0` |
| константы (`I`) | `addi`, `lui`, `ori` | `Rd <- Rs1 + Imm`; `lui` -- старшая половина, `ori` -- ИЛИ младшей |
| чтение памяти (`I`) | `lw`, `lb`, `lbu` | слово; байт со знаковым расширением; байт с нулевым расширением |
| запись памяти (`S`) | `sw`, `sb` | слово; младший байт |
| ветвление (`B`) | `beq`, `bne` | переход при равенстве / неравенстве |
| ввод-вывод | `in` (`I`), `out` (спец. `S`) | байт через порт; см. раздел ввод-вывод |
| управление | `jmp`, `jal` (`J`), `jr` (`I`), `halt`, `trap` | переход, вызов, возврат, остановка |

Остальные сравнения выводятся из `slt` и `seq`:
- `a < b` -- `slt Rd, Ra, Rb`
- `a > b` -- `slt Rd, Rb, Ra`
- `a >= b` -- `slt Rt, Ra, Rb` + `seq Rd, Rt, R0`
- `a <= b` -- `slt Rt, Rb, Ra` + `seq Rd, Rt, R0`
- `a != b` -- `seq Rt, Ra, Rb` + `seq Rd, Rt, R0`

Константы: значения из диапазона `Imm` -- одним `addi Rd, R0, imm` (трюк с `R0`). Произвольные 32 бита -- парой:

```text
lui Rd, upper16     ; Rd <- upper16 << 16, младшая половина очищена
ori Rd, Rd, lower16 ; Rd <- Rd | lower16
```

Деление и остаток: на ноль -- `trap 1`. `INT_MIN / -1` и `INT_MIN % -1` -- младшие 32 бита математического результата (`INT_MIN` и `0`).

## Управление

- `jmp Disp` -- безусловный переход
- `jal Disp` -- `R1 <- PC + 1`, переход
- `jr Rs` -- переход по адресу из регистра; специальная I-образная раскладка, `Rs` в битах 20--16; возврат -- `jr R1`
- `halt` -- нормальное завершение программы; слово `0xFC000000`, остальные поля нулевые; код завершения берётся из `R4`
- `trap code` -- системная I-образная команда с раскладкой `Op:6, zero:5, zero:5, Code:16`; код причины -- младшие 16 бит: слово `0xF8000000 | код`

## Ввод-вывод

Портовое ввод-вывод (PMIO): у портов собственное адресное пространство, не пересекающееся с RAM.

- `in Rd, port` -- в `Rd` заносится нулевое расширение байта из порта
- `out Rs, port` -- в порт уходит младший байт `Rs`
- порт `0` -- входной поток, порт `1` -- выходной; обращения к другим портам -- `trap 5`
- `in` -- I-формат: `Port` занимает поле `Imm` (биты 15--0), поле `Rs1` -- нулевое; `out` -- поле `Port` специального S-формата; у `out` источник занимает первый регистровый слот (биты 25--21); в обеих командах `Port` -- беззнаковые 16 бит (0--65535)
- входной буфер исчерпан: модель останавливает моделирование и фиксирует причину в журнале (требование `stream`: «если данные в буфере кончились -- останавливайте моделирование»); `in` возвращает только байты 0--255
- печать чисел -- не функция процессора: codegen порождает подпрограмму перевода `int` в десятичные байты через `div`/`mod` на 10

## Trap-коды

| Код | Причина |
| --- | --- |
| 1 | деление на ноль |
| 2 | неверный доступ к памяти: вне RAM или невыровненный `lw`/`sw` |
| 3 | превышение предела размера массива или пересечение кучи и стека |
| 4 | выход за границы массива или строки |
| 5 | обращение к несуществующему порту |
| 6 | неизвестный опкод |
| 7 | некорректная строка для `input_int` |
| 8 | строка для `input` содержит больше 1023 байт текста |
| 9 | отрицательная степень `a ** b` |
| 10 | отрицательный размер `new int[n]` |
| 0, 11--65535 | резерв |

Назначение trap-кодов зафиксировано в этой таблице. Команды `trap` добавляются кодогенератором в `src/translator/codegen.py`; их машинное кодирование определено в `src/machine/isa.py`. Коды 2, 5 и 6 относятся к поведению целевой модели процессора.

## Отличия от RISC-IV курса

| Вырезано | Причина |
| --- | --- |
| сдвиги `sll`/`srl`/`sra` и immediate-варианты | в языке нет сдвигов; сдвиг живёт как микрооперация в микрокоде `mul`/`div` |
| `xor`, `xori`, `andi`, `slti` | не порождаются codegen; инверсия булева -- `seq` с `R0` |
| `mulh` | арифметика 32-битная с заворачиванием |
| `beqz`, `bnez`, `blt`, `bge`, `bltu`, `bgeu` | выводятся из `slt`/`seq` + `beq`/`bne` |
| `jalr`, `mv` | вызовы прямые (`jal`), возврат -- `jr R1`; `mv` = `add Rd, Rs, R0` |
| `gp`, `tp`, caller/callee-saved разбиение | статика известна при компиляции; служебные регистры фиксированы |
| `%hi`/`%lo` и relocation | нет ассемблера и линкера; деление константы на половины делает codegen |
| спецзначения `div`/`rem` при нуле | вместо них `trap` |

Добавлено относительно RISC-IV: `lbu`, `trap` с кодами, `in`/`out` (вариант `port`), `mod`, масштабированные смещения переходов, `lui`/`ori` с 16-битными половинами без округления `%hi`.
